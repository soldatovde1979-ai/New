## 1. Обзор системы

SVO Docs Automation — CLI-инструмент, который сканирует кодовую базу проекта и автоматически генерирует/обновляет её техническую документацию в формате `spec.md` + `data.md` (тот же формат, в котором написан этот документ). Запускается локально или в CI (например, как шаг GitHub Actions при пуше в основную ветку), не требует постоянно работающего сервера.

## 2. Архитектура и стек технологий

1. **CLI-обвязка** — точка входа `svo-docs`, парсинг аргументов и подкоманд. Технология: Python 3.11+, `argparse` (без тяжёлых зависимостей на старте).
2. **Scanner (сканер репозитория)** — обходит файловое дерево проекта, собирает список файлов, извлекает докстринги/комментарии, сигнатуры функций. Технология: стандартная библиотека Python (`ast`, `pathlib`).
3. **Analyzer (анализатор)** — сопоставляет собранные данные с конфигом (`config/docs-automation.yaml`), опционально обращается к LLM для суммаризации сложных workflow. Технология: Python; LLM-вызов — через отдельный адаптер (см. `data.md`, раздел "Контракт LLM"), провайдер не зафиксирован.
4. **Generator (генератор)** — рендерит `spec.md`/`data.md` по Jinja2-шаблонам из `templates/`. Технология: Jinja2.
5. **Config (конфигурация)** — YAML-файл, описывающий источники, исключения, выходные пути. См. `data.md`.
6. **Drift-cache (кэш дрейфа)** — JSON-файл с хэшами последней сгенерированной документации, чтобы команда `check` могла определить, что документация устарела относительно кода. См. `data.md`.

## 4. Ключевые алгоритмы и workflows

### 4.1 `svo-docs generate` — генерация документации

1. CLI (`cli.py:main`) читает конфиг `config/docs-automation.yaml`.
2. `scanner.scan_repo(root, config)` обходит файлы проекта, применяя `ignore_patterns` из конфига, возвращает список файлов с ролями и извлечённые сигнатуры/докстринги.
3. `generator.render(scan_result, templates_dir)` подставляет собранные данные в `templates/spec.md.j2` и `templates/data.md.j2`.
4. Результат записывается в пути, указанные в `output.spec_path` / `output.data_path` конфига.
5. Хэши сгенерированных файлов сохраняются в drift-cache (`.svo-docs-cache.json`) для последующей проверки командой `check`.

### 4.2 `svo-docs check` — проверка актуальности документации

1. CLI повторяет шаги 1–3 из 4.1, но не перезаписывает файлы, а сравнивает результат с текущим содержимым `spec.md`/`data.md`.
2. Если содержимое расходится — команда завершается с ненулевым кодом выхода (для использования в CI как gate).

> ⚠️ Предположение: точный набор данных, которые сканер должен извлекать (только докстринги/сигнатуры, или также TODO-комментарии, схемы конфигов и т.д.), не уточнён — заложена базовая версия, расширяемая позже.

## 5. Правила разработки для AI-ассистента

- Не добавлять реализацию, выходящую за рамки того, что описано в `spec.md`/`data.md`, без явного запроса — это стартовый скелет, а не готовая система.
- Любое поле конфига или схемы данных, добавляемое в код, обязано быть отражено в `data.md` в том же коммите.
- Не привязываться к конкретному LLM-провайдеру в коде `analyzer.py`, пока провайдер не выбран явно (см. `data.md`, раздел "Контракт LLM").
